# 1.1 Your First StateGraph (Nodes & Edges)

### Introduction
In Phase 0 you ran a sanity check and compared LCEL with a single-node graph. This module goes deeper into **graph construction**: how to define state, register nodes, wire edges, compile, run, and visualize the workflow.

### Objective
Build a `StateGraph` from scratch, run it with `invoke()`, and inspect the graph structure so execution is no longer a black box.

### Concept

A LangGraph application is built in four steps:

1. **Define state** — a `TypedDict` describing shared data between nodes
2. **Add nodes** — Python functions that read state and return partial updates
3. **Add edges** — connections from `START` → nodes → `END`
4. **Compile & run** — `app = graph.compile()` then `app.invoke(initial_state)`

#### Core symbols

| Symbol | Meaning |
|---|---|
| `StateGraph(State)` | Builder for a graph with the given state schema |
| `START` | Virtual entry node — where execution begins |
| `END` | Virtual exit node — where execution stops |
| `add_node(name, fn)` | Register a step |
| `add_edge(a, b)` | Always go from `a` to `b` after `a` finishes |
| `compile()` | Produce a runnable app |
| `invoke(state)` | Run the graph once with initial state |

#### Node function contract

```python
def my_node(state: State) -> State:
    return {"field": new_value}  # partial update — other fields are preserved
```

Nodes receive the **full** current state and return only the fields they change. LangGraph merges the return value into state before the next node runs.

#### Single node vs. multi-node

```
Single:  START → greet → END
Multi:   START → trim → uppercase → END
```

Multi-node graphs pass the **same state object** through each step in order. This is the foundation for longer pipelines (RAG, agents, approval flows).

#### Visualization

```python
app.get_graph().draw_mermaid()
```

Returns Mermaid diagram text you can paste into documentation or render in notebooks. Seeing the graph on paper (or screen) makes debugging control flow much easier.

### Example

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    message: str

def greet(state: State) -> State:
    return {"message": f"Hello, {state['message']}!"}

graph = StateGraph(State)
graph.add_node("greet", greet)
graph.add_edge(START, "greet")
graph.add_edge("greet", END)

app = graph.compile()
app.invoke({"message": "LangGraph"})
# {'message': 'Hello, LangGraph!'}
```

### 2 Use Cases
1. **Text preprocessing pipeline:** `trim → normalize → validate` as explicit nodes before an LLM step—each step is testable in isolation.
2. **Onboarding workflow:** `collect_name → collect_email → confirm` as a linear graph you can later extend with conditional routing (Module 1.3).

### Real-World RAG & Agentic Context
In **Real-World RAG**, a retrieval pipeline is rarely one function. You often have distinct steps: `rewrite_query → retrieve → rerank → generate`. Modeling each as a node makes it obvious where latency or failures occur when you trace a bad answer.

In **Agentic Systems**, even before tools and loops, naming your steps as nodes establishes a discipline: every transition is declared, every state change is inspectable. That structure is what lets you add checkpointing and human-in-the-loop later without rewriting everything.

### Did you know?
`app.stream(initial_state)` yields events as each node completes—useful for progress UIs and debugging. You will use streaming heavily in advanced modules; getting comfortable with it early pays off.
